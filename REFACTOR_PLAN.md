# Refactor Plan: Dedupe shared code into `_shared/`

Goal: reduce copy-paste duplication across the 114 tools by consolidating vendored
libraries and common boilerplate into `_shared/`, without breaking the live PWA
(offline precache), print layouts, or any tool's behavior.

Status key: [ ] not started · [~] in progress · [x] done

---

## Audit findings (2026-08-10)

Measured across `Tools/*.html` (114 files) and per-tool subfolders:

**Vendored library copies (biggest win, ~2.5 MB of duplicate minified JS):**

| Library | Copies | Locations | Notes |
|---|---|---|---|
| `xlsx.full.min.js` | 2 | review-game-board/libs, final-grade-checker/libs | ~881 KB each, byte sizes differ → two different builds |
| `jspdf.umd.min.js` | 5 | image-to-pdf (has BOTH `lib/` AND `libs/` copies), blank-map-generator/lib, schedule/libs, final-grade-checker/libs | at least 3 different builds (365730 / 364861 / 364463 bytes) |
| `jsqr.js` | 4 | schedule-visualizer, escape-room-builder, classroom-timer, qr-code-generator (all `lib/`) | 3 identical + 1 older (256723 bytes) |

**Correction (Phase 1, 2026-08-11):** the "different builds" column above was
inferred from byte counts and was mostly wrong. Normalizing CRLF→LF before
hashing, there were only **two** genuinely different builds site-wide, both of
jsPDF:

| Library | Distinct builds actually found | Detail |
|---|---|---|
| `xlsx.full.min.js` | 1 | both copies are 0.18.5; the 22-byte gap was 22 CRLF line endings |
| `jspdf.umd.min.js` | 2 | 2.5.1 (four copies, two line-ending variants) and 2.5.2 (one copy, `image-to-pdf/libs/` — which was *orphaned*: the tool loaded the 2.5.1 copy from its `lib/` folder) |
| `jsqr.js` | 1 | all four identical; the 10,099-byte gap was CRLF line endings, not an older build |

Worth remembering for Phases 3–6: **compare content hashes with line endings
normalized, not file sizes.** Raw byte counts overstated the drift here by a
factor of three.

Folder naming is inconsistent: some tools use `lib/`, some `libs/`.

**Inline boilerplate duplicated across tool HTML files:**

| Pattern | Files | Notes |
|---|---|---|
| Service-worker registration snippet | ~83 | identical 5-line block, registers `../sw.js` |
| `:root` CSS variable block (theme palette) | ~84 | `_shared/theme.css` exists but only 16 tools reference `_shared/` at all |
| `@media print` styles | 78 | incl. identical `#printArea` block in 30 files |
| `.card` / `.app-header` / `.toolbar` CSS | ~59 | verbatim identical lines |
| `localStorage` save/load try-catch pattern | ~104 use localStorage; 14 share an identical setItem line | key names differ per tool |
| CSV export code | ~96 mention csv | needs closer per-tool audit |

**Existing infrastructure to respect:**

- `_shared/` already has: a11y.css/js, qr-scan.js, state-link.js, theme-toggle.js, theme.css, webrtc-pair.js. 16 tools use it. Extend this, don't invent a parallel location.
- `sw.js` hand-curates `PRECACHE_URLS` and requires a `CACHE_VERSION` bump whenever
  the file list changes. **Every phase below must update both.** Currently v44.
- Social/OG meta tags are generated by `Tools/board-check/sync-social-tags.mjs` —
  generated blocks are marked `gvb:social:start`. Do not hand-edit; not a dedupe target.
- A few tools have real test harnesses (`Tools/*/test/smoke.mjs`) — run them when
  touching those tools (schedule, seating-chart, name-picker, image-to-pdf,
  final-grade-checker).

**Accepted tradeoff:** tools stop being fully self-contained single files. This is
already true for every tool with a `lib/` folder, and the service worker precaches
`_shared/` so offline still works site-wide. What's lost is "download one .html file
and it works standalone" — for tools that currently have zero external references,
extraction should be weighed tool-by-tool in Phases 3–5.

## Phases

Each phase = one or more small PRs. Never touch all 114 files in one PR; batch ~10–15
tools. After each batch: bump `CACHE_VERSION` in sw.js, update `PRECACHE_URLS` if
paths changed, and smoke-test every touched tool in a browser (load, toggle theme if
present, print preview, save/reload state).

### Phase 0 — Conventions (one PR, no behavior change)
- [x] Decide and document in a new repo `CLAUDE.md`:
  - Vendored libraries live in `_shared/vendor/<name>/<file>` — one canonical version each.
  - Per-tool folders use `lib/` never `libs/` for anything that remains tool-specific.
  - Rule: any file added/renamed → update sw.js PRECACHE_URLS + bump CACHE_VERSION.
  - Rule: new tools must link `_shared/theme.css`, `_shared/a11y.js`, `_shared/sw-register.js` instead of inlining.
- [x] Update the tool-generator prompts in `prompts/` / `improvement prompts/` to match,
  so newly generated tools follow the conventions (otherwise drift returns immediately).
  (Done 2026-08-11: standard conventions block added to all 14 `prompts/*.md`
  files, three `libs/`-endorsing bullets corrected, and the improvement-round
  workflow in `improvement prompts/_tools-touched.md` step 3 now points at
  `CLAUDE.md`. `_shared/sw-register.js` itself is deliberately NOT created in
  this phase — that's Phase 2; CLAUDE.md documents the fallback until then.)

**What landed:**

- **`Tools/board-check/harness.mjs`, written from scratch.** The original
  board-check folder was never committed to this repo (verified with

    gap the image-to-pdf suite already documents and works around).

  and reasoning recorded in `CLAUDE.md` § Test tooling. `node_modules` is
  gitignored, nothing about how the site is served changed, sw.js untouched
  (test files are not precached). Setup: `npm ci && npx playwright install
  chromium`.
- **`Tools/image-to-pdf/test/smoke.mjs` unhardcoded** from its Linux sandbox
  (`/opt/node22/lib/node_modules`, `/opt/pw-browsers/chromium`): Playwright
  now resolves normally and picks its own Chromium, with a clear
  "run npm ci" message if missing. No assertions changed.
- **`Tools/board-check/check-social.mjs`** — a read-only validator for the
  `gvb:social` blocks (no write path). `sync-social-tags.mjs` was NOT
